## = 1.2.1 =

* **Fixed — plain-text emails arrived as HTML when "Multi-Part Plain Text" was on.** The setting is meant to add a plain-text version to HTML emails, but on SMTP and PHP Mail connections it was applied to every email. Giving a plain-text message an alternative body makes PHPMailer build `multipart/alternative`, and PHPMailer always labels that second part `text/html` — so the plain body went out declared as HTML, and mail clients displayed it that way. That covered most of WordPress's own mail: password resets, new-user and admin notifications, and the Email Test, which sends plain text. The option now only acts on emails that are actually HTML. The API mailers were unaffected; they already checked. Reported on the support forum by @dimalifragis.
* **Fixed — a PHP deprecation notice on every SMTP send.** Two places set `$phpmailer->Exceptions = true`, but PHPMailer has no such property — its switch is a protected `$exceptions`, set only through the constructor. The assignment never did anything; on PHP 8.2 and later it instead logged "Creation of dynamic property WP_PHPMailer::$Exceptions is deprecated" once per email, and PHP 9 will make it a fatal error. Both mailers were already created with exceptions on, so the lines are simply removed and nothing about sending changes. Verified that a failed SMTP send still returns `false` and still reports the real connection error.
* **New — Simulation Mode is now visible wherever you are.** Switching it on stops every email at the door, logged but never handed to a provider, and nothing on screen said so: the only trace was the toggle itself, several scrolls down the Settings tab. Turn it on by accident, or forget you turned it on deliberately, and the site simply stops mailing while every screen still looks healthy. An amber **Simulation Mode** badge now sits in SendForce's header on every one of its screens, and clicking it goes straight to the toggle that turns it off.
* **Email Test says it up front.** Starting a test send while Simulation Mode was on produced an error only *after* you had typed an address and pressed the button — the first and only hint that nothing could be delivered. The tab now carries a warning above the form explaining that mail is logged rather than sent, with a **Turn off Simulation Mode** button. The send itself is still refused, as before.
* **Both routes land on the toggle, not the top of the page.** The Settings tab is long, and the Email Simulation control sits well down it; the badge and the Email Test button now link to the control itself.
* At narrow widths the badge takes its own row above the navigation icons, rather than competing with them for space.

## = 1.2.0 =

* **Fixed — Microsoft 365 silently dropped every attachment.** `SendForce_API_Outlook::send()` accepted `$attachments` and never used them: the Graph `sendMail` payload carried no `message.attachments`, Microsoft answered HTTP 202, and the mail arrived — complete except for the files, in the recipient's inbox and in Sent Items alike. Attachments are now sent as Graph `#microsoft.graph.fileAttachment` resources. Reported on the support forum by @ydekinder against 1.1.3, with debug logs showing exactly this; present since the mailer was written.
* **Fixed — Zoho ZeptoMail dropped attachments the same way.** Found while checking whether the Microsoft bug was isolated: its payload never carried the files either. Now sent as ZeptoMail `attachments[]` entries. Every other API mailer was verified to put attachments on the wire.
* **Microsoft's 3 MB ceiling is now explained rather than hit.** `sendMail` carries attachments in the request body, which Graph caps at 4 MB; past roughly 3 MB of base64 it returns a bare 413 that reads like a server fault. Oversize attachments are now refused before sending, with the total size and the offending file names, and a suggestion to link the file or use SMTP for that message.

* **New — Setup screen after activation.** Activating SendForce used to drop you back on the Plugins list with a conflict warning stacked above it, which is the worst possible place to decide how to migrate. Activation now sends the admin who performed it, once, to a Setup screen that leads with migration: every active SMTP plugin SendForce can import from is listed with **Import settings** (the same preview → import → result panel used elsewhere) and **Deactivate**; plugins it cannot import from yet are listed separately with just Deactivate, since leaving two of them running means both fight over `wp_mail()`. Below that are the only two things that must be true before email works — a connection, and a test send — each showing as done once it is.
* **The redirect is deliberately narrow.** It fires only for the user who clicked Activate, only once (a 60-second transient that is deleted before redirecting), never on a bulk activation (WordPress adds `activate-multi`, and hijacking that request would strand the other plugins mid-activation), never on a network activation, and never on a site that already has a connection or has been set up before — so updating or reactivating an existing install does not hijack the page.
* **Changed — the conflict warning no longer follows you around the admin.** It was hooked to the global `admin_notices`, so it rendered on Plugins, Posts, the Dashboard and everywhere else. It now renders only on SendForce's own screens, and not on the Setup screen, which already lists the same plugins with the same buttons and more context.
* **An imported source now says so.** The button kept reading "Import settings" after an import had already happened, inviting people to run it again with no indication it had worked. Each source that has been imported from now shows an "Imported" badge and a quieter "Check again" button — in the Setup screen, the Settings tab card and the conflict notice alike. Re-running it is still allowed and still safe (it reports everything as already imported), it just no longer looks like outstanding work. Where the page does not reload, the button relabels itself as soon as the import finishes.
* **Fixed — uninstall left several caches behind.** The cleanup named transients one at a time and the list had drifted: the dashboard-stats cache, the per-range daily-stats caches and the alert-throttle records all survived an uninstall. It is now a single sweep over the plugin's own `sendforce_` transient prefix, so current and future keys are covered. Verified on a throwaway site by seeding every transient family the plugin can create and confirming nothing survives.
* **Fixed — admin scripts could be served stale from the browser cache.** The stylesheets were cache-busted with each file's modification time, but every script, and three of the stylesheets, were versioned by the plugin version alone. Any change to a file within the same version — a patched install, a hotfix, development — kept the cached copy, which is how the setup wizard's new return-to-wizard behaviour silently did nothing in a browser that had already loaded that release's `admin.js`. All of the plugin's own assets now use the file's modification time, so the URL moves whenever the file does. The vendored Chart.js keeps its upstream version number.
* **The finish is now reachable, and the order of attention is fixed.** Three UX problems went out with this: the "2 of 2 done" state could never be seen, because the test email is sent from another tab and Setup redirects away once a connection exists — a successful test started from Setup now returns here to a "You're all set" panel. The "Then explore" cards (Smart Routing, Email Log, Queue, Alerts) no longer appear before anything works; they are shown as a reward on completion. And only one action is ever styled as primary: when a plugin can be imported, importing leads and the manual "Set up a connection" steps back, and "Send a test" is never the primary action before a connection exists, since there is nothing to test yet.
* **The wizard now comes back to you.** Step 1 sends you to Settings to create a connection, and that link carries a `from=setup` marker; once the connection saves, Settings returns you to the Setup screen with step 1 ticked and the test-email step as the next action. Previously you were left on Settings with no way back — the wizard had quietly ended. The return is explicit (`resume=1`), so it is honoured even though Setup is otherwise retired once a connection exists.
* **Setup retires itself once the first step is done.** The screen exists to get a first connection in place; once one exists it has nothing left to offer, so opening it — from an old bookmark, the back button, or a reactivation — lands on the Dashboard instead. The one exception is the reload that follows an import started on that screen, since the import is what created the connection and its result is still waiting to be shown.
* **Importing on the Setup screen updates the screen.** Previously the import finished but the steps below it still read "Set up a connection", because they were rendered before the connection existed. The screen now reloads after a successful import, and the result ("Imported 2 connections", any Smart Routing rules, anything needing attention) is rendered server-side from a short-lived per-user transient rather than rebuilt from strings in JavaScript — so it stays translatable. The transient is only stored when the import was started from the Setup screen: an import run from the conflict notice or the Settings tab shows its result inline as before, and stashing it there would have surfaced a stale banner the next time Setup was opened. It is read once and deleted, so a refresh does not repeat it.
* **Fixed — a dead reactivation guard.** The activation redirect checked an option, `sendforce_setup_done`, that nothing ever wrote, so the check could never be true. Opening the Setup screen now records that it was shown, which is what makes "do not hijack the page on a later reactivation" actually work. Uninstall removes that option, the setup-redirect transients and the import-result transients, which were all missing from the cleanup sweep.
* **Fixed — a CSS class collision.** The Setup screen originally reused `.sendforce-setup-card` and `.sendforce-setup-steps`, which the Dashboard tab already owns, and silently inherited that card's gradient, flex layout and padding — the screen rendered with a green tint, misaligned content and a large empty gap. Everything here is now namespaced `sendforce-ob-`, with a test that fails if the Dashboard tab's class names reappear in this template. The hero no longer squashes the 913×118 wordmark SVG into a 46px square.
* **Tested** on a real throwaway site end to end: the plugin was activated through the actual Plugins page and the redirect chain followed (WordPress → `plugins.php?activate=true` → the Setup screen), an Easy WP SMTP configuration was imported from the Setup screen in a headless browser, and the Plugins page was confirmed clean afterwards. Unit coverage adds the redirect rules (first run, second run, bulk activation, configured site, prior setup, network activation), both screen states (with and without importable plugins), and the notice's new scope.

## = 1.1.3 =

* **New — import from WP Mail SMTP, FluentSMTP and Easy WP SMTP.** `SendForce_Importer` reads each plugin's settings through that plugin's own API — never its raw option — because both encrypt credentials and both let `wp-config.php` constants override saved values: WP Mail SMTP via `WPMailSMTP\Options` (applies `WPMS_*` constants, decrypts the libsodium-encrypted SMTP password), FluentSMTP via `fluentMailGetSettings()` (decrypts AES-encrypted fields under its versioned `ENCRYPTED_FIELDS` rules — e.g. the SES access key is only encrypted from `encrypt_version` 2, so decrypting a v1 site's plain value would corrupt it). Using their readers keeps the importer correct when either plugin changes its storage, which is why the source plugin must be active to import. WP Mail SMTP's own FluentSMTP importer reads the raw option, which predates FluentSMTP's encryption and imports ciphertext.
* **Easy WP SMTP shares WP Mail SMTP's settings design** — an `Options` class with `get( $group, $key )` and `is_const_defined()`, one active mailer, the SMTP password encrypted with libsodium and decrypted on read, and the same optional network-wide mode — so both are handled by one reader (`plan_options_api()`) keyed by namespace, rather than a second copy of the mapping. Keys that exist on only one of them (Easy WP SMTP's Gmail One-Click Setup, WP Mail SMTP's Pepipost) read back empty on the other, so the shared path stays correct. Easy WP SMTP's mailers map across in full: PHP mail, SMTP, SendLayer, SMTP.com, Brevo/Sendinblue, Amazon SES, Gmail, Mailgun (with region), Mailjet, MailerSend, Mandrill, Outlook, Postmark, Resend, SendGrid, Elastic Email, SMTP2GO and SparkPost; Zoho Mail is reported as not importable, as it is for WP Mail SMTP.
* **Two things the admin must act on are now flagged instead of failing silently.** A SparkPost account on the **EU region** is flagged, because SendForce only talks to `api.sparkpost.com` and an EU key would be rejected there — this affects WP Mail SMTP imports too, which previously copied the key with no warning. A Gmail or Outlook connection set up with Easy WP SMTP's **One-Click Setup** has no app credentials stored on the site to copy, so the import explains that you need to create your own Google or Microsoft app rather than leaving an empty connection behind.
* **What comes across.** Connections (SMTP, PHP mail, Amazon SES, SendGrid, Mailgun incl. EU region, Brevo/Sendinblue, Postmark, SparkPost, Mailjet, SMTP.com, SendLayer, Elastic Email, SMTP2GO, Resend, Mandrill, MailerSend, Pepipost, Gmail, Microsoft 365), the From identity when the source forces it, primary and fallback, and FluentSMTP's per-sender `mappings` as Smart Routing `from_email` rules (otherwise its extra connections would never be used). SMTP hosts SendForce has a preset for are matched to that provider. Credentials are re-encrypted with SendForce's own key.
* **Safe by design.** A preview (secrets stripped) is shown first. Importing only adds connections: an existing SendForce primary, fallback or Sender Identity is never replaced. Each imported connection carries an `import_key`, preserved when the connection is later edited, so re-importing reports "already imported" instead of duplicating. Imported routing rules are de-duplicated by what they do (target connection + exact condition), not by their label, which is translated and would change with the site language. If Smart Routing's master switch is off, the switch is left alone and the result says the new rules won't apply until it's turned on. Gmail and Microsoft 365 API connections import their app credentials but not OAuth tokens and are flagged for re-connection (over SMTP with an app password they import like any SMTP connection); credentials kept in `wp-config.php` (WP Mail SMTP constants, FluentSMTP `key_store = wp_config`) are not copied into the database and are flagged instead. Mailers with no SendForce equivalent (WP Mail SMTP's Zoho Mail, FluentSMTP's ToSend and Cloudflare) are listed as not importable, and a non-default Postmark message stream is flagged.
* **UI.** An "Import settings" button on the conflict notice row for each importable plugin opens an inline preview → import → result panel. The same button is on the Settings tab in an "Import from another plugin" card, shown whenever an importable plugin is active — dismissing the notice for 30 days would otherwise hide the importer. Panels are `aria-live="polite"` so screen readers announce the preview and result. The panel builds every element with `textContent`, since names and notes originate in another plugin's settings. Endpoints `sendforce_import_preview` / `sendforce_import_run` require a nonce and `manage_options`.
* **Tested** against this site's real FluentSMTP settings (encrypted SMTP password decrypted correctly; preview contained no secret) and real WP Mail SMTP settings, plus fixtures encrypted with each plugin's own crypto at FluentSMTP `encrypt_version` 1 and 2: provider mapping, decryption, routing-rule creation, re-import without duplicates, existing settings respected, wp-config constants not copied, unsupported mailers, inactive source, Gmail/Microsoft 365 over SMTP, a FluentSMTP connection with no provider (skipped), an existing SendForce connection with no id (no PHP warning), re-import after a site-language change (no duplicate rules), Smart Routing switched off, and the Settings card with the notice dismissed. Every run was wrapped in a rolled-back database transaction, so nothing persisted to the site. The panel's flow was tested by running the real script against a simulated DOM that throws on any `innerHTML` use, with a hostile connection name.
* **WP-CLI.** `wp sendforce import list|preview|run <source>` drives the same importer from the command line: `list` shows which sources are active and importable, `preview` prints the plan as a table and changes nothing, and `run` asks for confirmation (`--yes` skips it) before importing, then reports the connections and routing rules created plus anything needing attention. The table is built from `preview()`, which strips secrets, so no credential is ever printed. On Multisite, `--url=` picks the site. Reading WP Mail SMTP's network-wide settings requires `manage_network_options` in the browser; over WP-CLI with no logged-in user that check is skipped, since whoever runs the command already has shell and database access — a `--user=` is still honoured.
* **Multisite.** Importing is per site: the connection, sender identity and routing rules land on the site you import from, and nothing is written to another site. WP Mail SMTP can instead be configured once for the whole network (`general.network_wide`), in which case its settings live on the main site and are encrypted with the main site's key — the importer reads them there via `switch_to_blog( get_main_site_id() )`, and only for a user with `manage_network_options`, since those credentials are hidden from site admins. FluentSMTP stores settings per site, so it needs no special handling. Verified on a real throwaway Multisite network (2 sites, network-activated plugins, a non-super-admin site administrator): per-site setup, tables, cron and log isolation; network-wide import allowed for the network admin and refused with a clear message for the site admin; per-site import when the network-wide switch is off; conflict detection for network-activated plugins; and site deletion dropping that site's tables. The network and its database were created for the test and deleted afterwards.
* **Changed — more strings translatable.** WP-CLI command output (`wp sendforce test|queue|logs`), the Gmail and Microsoft 365 "not signed in / credentials missing" errors shown in the email log, the routing rule card's fallback titles and the `(unnamed)` connection labels now go through `__()` with translator comments. The Gmail and Outlook messages also lost their internal debug markers (`PRECHECK`, `MARKER_v1024_PRECHECK`) and key-length dumps in favour of a sentence that says what to do. Scans confirm every `__()`-family call in the plugin uses the `sendforce-mail-relay` domain, every placeholder string has a translator comment, no user-facing literal text is left in templates or PHP, and every key the admin, routing and import scripts look up is present in the localized bundles. Cron schedule `display` labels stay literal on purpose: `cron_schedules` fires before the textdomain loads, and WP 6.7+ warns about translating that early.
* **Changed — sidebar label.** The admin menu item is now "SendForce" instead of the "SF Mail Relay" abbreviation; it still fits on one line. The page title stays "SendForce Mail Relay".

## = 1.1.2 =

* **New — WordPress Multisite support.** Network Activate only fires the activation hook on the main site, and sites created later never fire it, so on a network every other site ran without its tables: emails sent from those sites weren't logged ("table doesn't exist"), queuing fell back to immediate sending, default settings were missing, and the daily log cleanup was never scheduled. Setup is now done per site by `sendforce_maybe_setup_site()` on `plugins_loaded`: a single autoloaded-option check (`sendforce_db_version` against `SENDFORCE_VERSION`) on every request, running `SendForce_Activator::setup_site()` (default options, cron events, then tables, which record the version last) once per site per plugin version, on whatever request reaches the site first, front-end and cron included. It replaces `sendforce_maybe_upgrade_db()`, which only ran for admin requests and ran a `SHOW TABLES` query on every admin page load. No activation-time loop over sites, so large networks can't time out.
* **Setup lock.** Simultaneous first visits could each run setup and schedule duplicate cron events. Setup now takes a per-site lock with an atomic `INSERT IGNORE` on the unique `option_name` (`add_option()` can't serve as a lock: it's an `INSERT … ON DUPLICATE KEY UPDATE`, which overwrites instead of failing), takes over a lock older than a minute with a compare-and-swap `UPDATE`, and re-reads options from the database after acquiring it, since each request starts with its own cached copy. Verified: 3 rounds of 8 simultaneous first visits ran setup exactly once each and left exactly one event per cron hook.
* **New — site deletion and network-wide cleanup.** Deleting a site drops its SendForce tables (`wpmu_drop_tables` filter); core only drops tables it knows about. Network Deactivate clears cron events on every site, and uninstall removes tables, options, transients and cron events from every site, with network-shared user meta removed once.
* **Fixed — uninstall left the queue's per-minute pacing counters** (`sendforce_rl_*` transients from 1.1.0) and the setup lock option behind.
* **Tested on a real throwaway Multisite network** (subdirectory install): a site that existed before Network Activate, one created after it, a 2nd visit (setup did not run again), site deletion, Network Deactivate, uninstall, and live vs stale setup locks.
* **Fixed — API connections ignored the From chosen by the sending plugin.** API sends short-circuit `wp_mail()` at `pre_wp_mail`, before core parses the `From:` header and applies the `wp_mail_from` / `wp_mail_from_name` filters, and the API mailer then always used Sender Identity or the admin email. So with Sender Identity empty, WooCommerce's store address (set through `wp_mail_from`), or a form plugin's `From:` header, was replaced with the admin email — and the same email got a different From depending on whether its Smart Routing rule picked an SMTP or an API connection. `SendForce_API_Mailer::apply_message_from()` now resolves the From the way core does (header parsed exactly like `wp_mail()`, then both filters, with core's `wordpress@<host>` default) and is called before every API send, primary and fallback. Sender Identity is itself a `wp_mail_from` filter, so it still overrides everything. When nothing chose a From (no header, and no filter changed core's default) the previous admin-email fallback is kept, so emails that never had a From don't change address. A filtered value that isn't a valid address (including one carrying CR/LF) falls back. Gmail and Microsoft 365 API connections opt out via `$from_bound_to_account`: Microsoft 365 rejects any From other than the mailbox, and Gmail rewrites it.
* **Docs — "Which From address do my emails use?"** FAQ entry, and an upgrade notice: setups whose provider accepts only specific verified addresses should set Sender Identity, since plugin-chosen addresses are now used.
* **Tested end-to-end** through `send_via_api()` with real provider classes and the HTTP request intercepted: plugin `From:` header, a WooCommerce-style filter, Sender Identity override, Microsoft 365 opt-out, CR/LF and invalid addresses, array headers with a quoted name, Mailgun's form-encoded payload, the no-From fallback, and a Smart Routing rule sending through a different API connection than the primary.
* **Docs — WP-CLI FAQ.** The readme listed only 4 of the 9 `wp sendforce` commands. A new "Does it support WP-CLI?" FAQ lists all of them (test; queue process / stats / clear; log list / tail / count / delete; sysinfo), with the Multisite `--url` flag and running the queue from a server cron.

## = 1.1.0 =

* **New — per-connection sending pace.** Each connection has a "Max emails per minute" setting (0 = unlimited). When the Email Queue sends, it works out which connection each email will go through — the Smart Routing target if a rule matches, otherwise the primary — and skips the email for this run (leaving it queued, unclaimed) once that connection has used its allowance for the current UTC minute. Nothing sleeps, so runs stay short. The queue fetches a wider candidate window (5× the batch size, max 1,000) than it sends, so a backlog on one rate-limited connection can't starve the others. Every attempt counts against the allowance, failures included, and a fallback recovery also counts against the fallback connection. Per-minute counters are transients; parallel runs can overshoot a limit by a send or two, but never send an email twice. The router now records the chosen connection in the merged settings as `_connection_id`, and the queue's prediction mirrors core's `wp_mail()` attributes (including WP 6.9+'s `embeds`) so the router's per-request cache returns the same answer at send time, round-robin rules included.
* **Improved — queue runs every minute while enabled, with a time budget.** While the Email Queue is enabled, the `sendforce_process_queue` event uses a new `sendforce_every_minute` schedule (was every 5 minutes); while it is disabled it stays on the 5-minute schedule, so sites that don't use the queue don't spawn WP-Cron's background request every minute. `SendForce_Queue::ensure_schedule()` runs on `init` and moves the event whenever it doesn't match `desired_schedule()` (on update, and whenever the queue is toggled), and refuses to clear the old event unless the replacement schedule is registered. Each run stops sending after 20 seconds (filter: `sendforce_queue_time_budget`), leaving the rest queued for the next run, so a large batch can't overrun a host's PHP worker limit. The batch size still caps sends per run.
* **Fixed — API connections bypassed the queue, and could double-send.** The queue's `pre_wp_mail` interceptor and the API sender were both at priority 10, and the API sender was registered first. So with the queue enabled, API-mode emails (Gmail API, Amazon SES, SendGrid, …) were delivered immediately and never queued; and while the queue was processing, the interceptor returned `null` without looking at what earlier filters returned, discarding the API sender's result so core sent the same email again through PHPMailer. The interceptor now runs at priority 3 (after Simulation Mode, before Smart Routing and the API sender), and while processing it passes through any earlier result instead of discarding it.
* **Fixed — overlapping queue runs could send the same email twice.** Rows were selected and then marked `processing` in separate statements, so two overlapping runs (a cron tick plus "Process Queue Now", or two cron workers) could both send a row. Each row is now claimed with a single conditional `UPDATE … WHERE id = ? AND status IN ('queued','failed') AND attempts = ?`; only the run that gets affected-rows = 1 sends it. Verified with two concurrent PHP processes draining the same 40-row queue: the two interleaved (24/16 split) and every email was sent exactly once.
* **Improved — Queue tab shows the last error.** The queue has stored each attempt's real provider error since 1.0.26, but the Queue tab never displayed it. Failed and retrying rows now show it under the status badge (escaped, truncated, with the full text on hover).
* **Changed — roadmap without dates.** Every roadmap card on the What's New tab carried a month and version (e.g. "June 2026 (v1.1)"), all of which had passed, and the "Coming next (v1.1)" group promised a Setup Wizard and Domain Health Checker that are not part of this release. Cards no longer show dates or versions (their status badge and group already convey order), so they can't go stale; those two items moved to the Planned group. The "Rate Limiting" card was narrowed to what's still outstanding (hourly, daily and monthly caps), since per-minute pacing shipped in this release. A comparative claim ("No other free SMTP plugin offers this") was removed, in line with the WordPress.org guideline on comparative statements.
* **Docs — corrected the Smart Routing description.** The readme said rules can target "a round-robin pool". The routing engine supports round-robin, but the rule editor has no way to create one yet, so the claim was removed.
* **Fixed — Smart Routing state could leak under queue mode.** Routing swaps in a rule's connection settings and restores them on `wp_mail_succeeded` / `wp_mail_failed`. When the queue then short-circuited the send, neither hook fired, so later emails in the same request used the routed connection. Because the interceptor now runs before routing, routing never runs for an email that is only being queued.

## = 1.0.37 =

A consolidated release rolling up the credential-encryption hardening, the fixes from a full-feature audit of the queue/router/lifecycle, and full JavaScript translatability of the admin UI.

* **Fixed — credentials lost when security keys/salts are regenerated.** Saved SMTP passwords and API keys were encrypted with a key derived from `wp_salt('auth')`, which is rotatable — security plugins' "regenerate security keys", host migrations, and site/staging clones all change it, which permanently broke every stored credential. Because decryption fails closed, the connection still *looked* configured while sending with an empty password, so mail silently stopped and users blamed whichever plugin update came next. Credentials are now encrypted with a dedicated random secret in the `sendforce_enc_key` option that never rotates; the old salt-derived key is kept as a decrypt-only fallback and a one-time migration re-encrypts existing credentials on upgrade. Nothing needs re-entering, and future salt rotations are harmless. Values that genuinely cannot be decrypted are left untouched rather than overwritten.
* **Fixed — passwords containing `<`, `>` or `%` were corrupted on save.** Secrets were run through `sanitize_text_field()` (which strips tags, removes `%xx` octets and collapses whitespace), so the stored value was not what was typed — surfacing as an authentication failure that looked like a wrong password. Secrets are now stored verbatim (encrypted at rest, never rendered as HTML), trimmed only of surrounding whitespace to catch copy-paste newlines.
* **Fixed — alert-channel secrets corrupted, and their output hardened.** The same corruption affected notification-channel credentials (Telegram/Slack bot token, Pushover user key and API token) and the Amazon SES access key; all are now stored verbatim. Because channel settings are emitted into the Alerts screen as JSON, the escaping moved to the output: `wp_json_encode()` there now uses `JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT`, so a stored value containing a closing script tag can no longer terminate the inline script early.
* **Added — warning when a credential cannot be read.** A dismissible admin notice now names any connection whose stored credential cannot be decrypted and links straight to Settings to re-enter it, instead of silently attempting to send with an empty password.
* **Fixed — duplicate sends with the queue enabled on positive-UTC timezones.** The queue's processing "lease" was written in UTC (`current_time('timestamp', true)` + `gmdate()`) while everything else used site-local time, so on a positive-offset site (e.g. UTC+6) the lease landed hours in the past and orphan recovery reclaimed a row that was still being processed — a concurrent run, or the "Process Queue Now" button, then re-sent the same email. (On negative offsets, genuinely crashed rows sat stuck ~8 hours instead of 10 minutes.) The lease is now computed in the same site-local frame as `$now`. A narrower SELECT-then-UPDATE race between two truly concurrent runs remains and is tracked for a follow-up release.
* **Fixed — silent email loss when a message can't be queued.** `intercept_mail()` short-circuited `wp_mail()` with `true` even when `add_to_queue()` returned `false` (DB error, missing table, oversized row), so the caller — WooCommerce, a form plugin, a password reset — recorded a successful send while the email vanished. It now returns `null` so WordPress core delivers the message synchronously instead of dropping it.
* **Fixed — uninstall left data behind.** Uninstalling now drops the `sendforce_routes` table and deletes the `sendforce_routing_enabled` option, the `sendforce_broken_credentials` transient, and the per-user notice meta, none of which were cleaned up previously.
* **Fixed — round-robin routing could select nothing.** `pick_connection_settings()` indexed the connection-id list positionally after `array_filter()` (which preserves keys), so a gap (e.g. `"1,,3"` left by a since-deleted connection) could hit an undefined index and pick no target. The list is now re-indexed with `array_values()` first.
* **Improved — the admin UI's JavaScript strings are now translatable.** Text produced by `admin.js` and the Smart Routing builder `routing.js` (dynamic field labels, button states, confirmation dialogs, the Gmail/Microsoft 365 OAuth flow, and routing condition/operator/preset labels) was hardcoded English in every locale. Both scripts now read their strings from a `wp_localize_script()` bundle populated with `__()` on the PHP side, via `sfT()` / `rT()` helpers supporting `%s` / `%d` substitution, with English fallbacks and escaped output — so translate.wordpress.org now delivers the JS translations automatically. (This plugin has no `@wordpress/i18n` build pipeline, so the fix is `wp_localize_script()` rather than `wp_set_script_translations()`, which would be inert here.)
* **Fixed — "updated to vX" notice would not go away.** It only recorded itself as seen when dismissed via the small "×" button; clicking **See what's new** navigated away without marking it seen, so it reappeared on the next page load. The button now also dismisses it permanently, using `navigator.sendBeacon` so the request survives the navigation it triggers.

* Security: **MIME header-injection guard on the Amazon SES / Gmail raw-MIME path.** `build_raw_mime()` assembled RFC 2822 headers by concatenation, and `encode_header()` only neutralized non-ASCII values; the To/Cc/Bcc/Reply-To/From address headers were not sanitized at all. A component forwarding untrusted input into `wp_mail()` (e.g. a contact form) could therefore inject a CR/LF and add a `Bcc:`, an extra `To:`, or a forged body to the raw message SES/Gmail sends — a path that bypasses PHPMailer's normal CRLF protection. CR/LF/NUL are now stripped from every header-bound value (subject and from-name via `encode_header()`, addresses via a new `header_addr()` helper).
* Fix: **Encrypted credential storage could intermittently corrupt a stored secret.** `encrypt_password()` joined the 16-byte binary IV to the ciphertext with the literal delimiter `::`, and `decrypt_password()` split on it — so an IV that happened to contain the bytes `0x3A3A` (~1 in 4,400) split mid-IV and failed to decrypt, silently breaking that connection's authentication. The format is now `sf2:` + base64(IV . ciphertext) with the fixed-length IV sliced off by length, eliminating the collision. Credentials saved in the old format still decrypt (and migrate to the new format the next time they're saved), and decryption now fails closed — returning an empty string on a damaged/tampered value rather than leaking the raw ciphertext as if it were the password.
* Fix: **Duplicate send + Simulation Mode bypass with the queue enabled.** The one-shot test-send bypass in `SendForce_Queue::intercept_mail()` was evaluated before the "another filter already handled this send" guard. With an API connection, the API mailer had already delivered the email and returned a short-circuit value, but the bypass branch discarded it and returned null — so WordPress core fell through to PHPMailer and sent the email a second time. The same ordering let a test send slip past Simulation Mode. The handled-send guard now runs first, and the bypass flag is consumed up front so it can't leak to a later send in the same request.
* Fix: **Fallback-recovered email re-queued and re-sent.** With the queue enabled and an SMTP-primary connection plus a fallback, core's `wp_mail()` returns false even when the fallback connection actually delivered the email (it reports the primary's failure). `process_queue()` read only that boolean and re-queued the row, re-sending via the fallback on the next cron run. It now consults `SendForce_Mailer::$last_send_used_fallback` (reset before each send) and treats a fallback recovery as success.

* Security: **SSRF hardening on alert webhooks.** Previously the five user-supplied webhook channels (Slack, Discord, Microsoft Teams, Google Chat, and the generic Webhook) posted to whatever URL the admin entered with no destination validation. A compromised or careless admin account could point a webhook at internal infrastructure — a cloud provider's instance-metadata endpoint (`169.254.169.254`), a database admin panel on `127.0.0.1`, or a service on the private `10.x`/`172.16-31.x`/`192.168.x` network — and use SendForce as a blind request proxy to probe or exfiltrate from it. A new private helper `SendForce_Alerts::is_safe_webhook_url()` now runs before every webhook send: it validates the URL with `wp_http_validate_url()` (which enforces the http/https scheme and rejects credentialed URLs), resolves the host to its IP address(es) — IPv4 via `gethostbynamel()` and IPv6 via `dns_get_record()` — and rejects the request if **any** resolved address falls in a private, loopback, link-local, or reserved range (using PHP's `FILTER_FLAG_NO_PRIV_RANGE | FILTER_FLAG_NO_RES_RANGE`). * Fix: **RFC-compliant attachment filename encoding, plus a header-injection guard.** Attachment filenames were being placed verbatim into `Content-Disposition` headers in two places: the multipart/form-data builder used by Mailgun, and the raw RFC 2822 MIME builder used by Amazon SES and Gmail. Two problems resulted. (1) A filename containing non-ASCII bytes — common with WooCommerce PDF invoices, contact-form uploads, or LMS certificates named in accented or non-Latin scripts — arrived as mojibake or was rejected/silently dropped by the receiving provider. (2) A filename containing a CR/LF could inject arbitrary MIME headers into the request body. Both builders now route the filename through a sanitizer that strips CR/LF, provides a safe ASCII fallback in the legacy quoted `filename="..."`/`name="..."` parameters, and — when the name carries non-ASCII bytes — adds the extended `filename*=UTF-8''…` / `name*=UTF-8''…` parameters (RFC 5987 for multipart/form-data, RFC 2231 for raw MIME) that Gmail, Outlook and Apple Mail all honour, recovering the true UTF-8 name. Verified against ASCII names, accented names (résumé.pdf), embedded quotes, and CR/LF injection attempts.
* Performance: **Cached dashboard and chart statistics with automatic invalidation.** `SendForce_Admin::get_dashboard_stats()` ran two lifetime `COUNT(*)` queries on every single dashboard page load, and `get_daily_stats()` ran one `COUNT(*)` per day per status — up to 180 separate queries for the 90-day chart range — on every chart AJAX request. The cache is invalidated immediately whenever the log table's row counts change — a new send is logged (`insert_log`), the retention cron prunes old rows (`cleanup_old_logs`), or a row/rows are deleted (`delete_log`, `bulk_delete`) — via a shared `SendForce_Logger::flush_stats_cache()` helper, so the figures are never stale after real activity. ## = 1.0.24 =

* **Fix (critical for OAuth users): Microsoft 365 / Gmail "Connect with provider" no longer fails with `AADSTS50011` / redirect URI mismatch.** Root cause: the authorize URL was built with `add_query_arg()`, which does NOT URL-encode the values it inserts.
